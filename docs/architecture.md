# 设计思路与第一性原理（Architecture & First Principles）

为什么是这个项目、为什么长这样、它从哪些同类项目里吸收了什么、又在哪里做了改进。
本文是设计决策的"思考记录"，不是使用手册（使用见 README，规范见 `conventions.md`）。

---

## 1. 第一性原理：我们要解决什么"真问题"

抛开"做个知识库报告工具"这种表面需求，往下一层问：

> **企业知识库检索的价值，最终要落到"可被信任、可被复用、可被分享"的文档上。**
> 而今天的现状是——检索结果停留在聊天窗口，随会话消失；AI 生成内容真假难辨，没人敢直接拿去汇报。

由此导出三个不可妥协的约束，构成项目的"第一性原理"：

1. **可信 > 好看**：宁可承认"这里没数据"，也不能编造一个看起来合理的结论。
2. **可追溯 > 流畅**：每个论点都要能一键跳到原始出处。
3. **可复现 > 一次性**：同样的输入必须产出同样的报告，否则无法审计、无法迭代。

这三个约束直接决定了后面的技术选型。

## 2. 从同类项目吸收了什么

立项前调研了 GitHub 上三类相近项目，取其长、避其短：

### 2.1 学术/综述生成类（解决"可信、可追溯"）
- **scholar-rag**：零幻觉、必溯源的检索增强综述。→ 吸收：**"每个论点绑定出处"** 的角标机制。
- **automated-slr-generator**：PRISMA 式透明检索流程，证据链可追溯。→ 吸收：**"检索过程可视化"**（把 query / 命中 / 去重聚合画出来）。
- **AI-Literature-Review-Generator**：PDF → 综述 + APA 引用 pipeline。→ 吸收：**"数据 → 内容 → 渲染"三段式 pipeline** 的工程结构。

### 2.2 企业知识库 / Agent 类（解决"落地形态"）
- **arkon / 53AIHub / FastGPT**：企业知识库 + MCP 接入 + 权限管控。→ 吸收：**四级权限、多端问答入口**作为综述里"工程要点"的论述框架（来自真实检索内容，非空谈）。

### 2.3 我们的差异点（创新）
同类项目大多是"通用框架"或"学术玩具"，缺一个**把"真实检索 → 可分享报告"做成闭环、且零依赖可离线**的轻量方案。我们的创新落在三点：

1. **单文件、全资源内联、零外部依赖**：一份 HTML 即一份可审计的资产，不依赖任何 CDN / 构建链。
2. **数据/内容/渲染三层分离**：`spec.json` 是"证据台账"，`body.html` 是"论点"，`review_generator.py` 是"排版机"——改样式不碰数据，改数据不碰代码。
3. **诚实缺口标注机制**：把"知识库没覆盖到的方向"做成一等公民（示例中的 Prompt 工程），而非用生成模型脑补。

## 3. 架构：三层分离

```
┌─────────────┐   ┌──────────────────┐   ┌────────────────────┐
│  数据层      │   │  内容层           │   │  渲染层             │
│ spec.json   │ + │ body.html        │ → │ review_generator.py │ → report.html
│ (真实检索)   │   │ conclusion.html  │   │ (纯标准库, 内联CSS) │
└─────────────┘   └──────────────────┘   └────────────────────┘
   不可编造          论点+角标               确定性输出
```

- **数据层**只存事实：query 统计、去重聚合、来源 URL 与标签。它是"证据台账"，也是审计入口。
- **内容层**是人类/AI 对证据的**综合叙述**，用 `[n]` 角标显式绑定到数据层的 `references`。
- **渲染层**是确定函数 `f(spec, body, conclusion) = html`，**无随机性、无网络、无外部资源**，因此可复现。

---

## 4. 为什么是"单文件内联 HTML"而不是 Web 应用

| 维度 | 单文件内联 HTML | 完整 Web 应用 |
|------|----------------|--------------|
| 可分享 | 微信/邮件直接发，双击即开 | 需部署、需登录 |
| 可审计 | 一份文件即一份资产 | 代码+数据+运行态分离 |
| 可复现 | 同输入同输出 | 受环境/依赖影响 |
| 成本 | 0 依赖、0 运维 | 服务器/域名/CI |

对企业内部"把检索沉淀成文档"的场景，单文件是 Pareto 最优：覆盖 90% 需求，成本近乎为零。若未来需要扩展（多人协作、自动定时生成），再在 `src/` 之上叠加服务层即可，不影响现有产物。

## 5. 真实性优先的工程取舍

- **不调用大模型"补全"内容**：综述正文由人/AI 基于真实 snippet 撰写，生成器只做排版，不生成事实。
- **耗时条形图按真实 `took_ms` 比例**：基准取最长耗时（96ms=100%），其余按比例，避免"看起来差不多"的失真。
- **去重聚合透明**：21 次命中 → 7 唯一文档 → 5 引用 + 2 容器排除，每一步都在报告里写清楚。

---

## 6. 未来演进方向（保持第一性原理不变）

- **接入乐享 MCP**：把"检索 → 填 spec → 生成"自动化，人只做"综合叙述"这一步。
- **多知识库交叉检索**：跨团队/跨库去重聚合，仍是同一份 `spec.json` 结构。
- **导出 Markdown / PDF**：渲染层增加输出适配器，数据层与内容层不动。
- **spec.json Schema 校验**：在 CI 里卡住"引用序号不连续 / 角标越界 / URL 缺失"等错误。

> 演进原则：无论加多少功能，**"可信、可追溯、可复现"三条红线不动**，新能力只能增强、不能削弱它们。
